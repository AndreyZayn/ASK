# Install through your agent

ASK is designed to be installed through a conversation with a local agent. The owner gives the prompt in the [README](../README.md); the agent performs the steps below. These are installation instructions, not authorization to install during a code review or a delegated task with `KB_ACCESS: none`.

## Installation checklist for the agent

1. **Choose the owner's locations and runtime.** Ask only for missing choices: a new private workspace folder, the owner's private GitHub repository name, and the runtime being connected. Keep the public checkout outside the private workspace. Never initialize over an existing vault. Use [the upgrade guide](upgrades.md) or [recovery guide](backup.md) when appropriate.
2. **Check prerequisites.** On macOS, check Python 3.9+, Git, GitHub CLI, and the selected agent runtime. Help the owner authenticate GitHub using its normal login flow; never request credentials in notes or put them in the vault. Choose the repository-local commit identity before the first backup: preserve existing local values, or use the documented GitHub noreply default/user-chosen identity in [install.md](install.md#choose-the-git-commit-identity); do not silently change global Git settings. Obsidian is optional. The public checkout is needed for initial setup; afterward, use the installed `ASK/system/scripts/ask.py` and guides under `ASK/system/docs/`.
3. **Create the complete ASK folder and backup.** Run the setup command in [install.md](install.md) with the actual choices. Verify `Knowledge Base/`, `system/scripts/`, and `artifacts/` are inside the selected ASK folder. After setup use its own scripts, including for runtime enrollment and scheduled backup. Clearly explain that scheduled backup covers eligible vault notes; artifact files require an explicit reviewed checkpoint. Check that the GitHub destination is private and the initial backup succeeds. Explain a local-only or offline pending state accurately. Scheduled backup is optional; enable it only when the owner chooses it.
4. **Persist the bootstrap in the real runtime.** Setup supports managed global instructions for Claude Code, Codex, Amp, Droid, and Antigravity. For other runtimes, follow the manual output and that runtime's supported persistent-instruction mechanism. The instruction must point to this owner's vault and read `date.md`, `INDEX.md`, `agents.md`, then `knowledge-map.md` at the beginning of a session. Preserve unrelated instructions. Merely reading these files once, or adding a row to a roster, does not complete runtime registration.
5. **Register identity and document observed capabilities.** Complete [agent onboarding](onboarding.md): reconcile a stable local ID, runtime/surface, role, agreed scope, and responsibility in the existing roster; inventory all skills exposed in current-session metadata when feasible, plus scoped tools and integrations; record only supported observations, source, date, and limits in the owner's capability catalogs. The installation request authorizes this narrow registration/documentation work, not new installations or broader access. `agent onboarding` can prepare read-only plans and proposed rows; the installing agent reviews and applies the authorized notes through the existing continuity/checkpoint process. `setup` does not fill these notes automatically, and `doctor` does not certify that they are complete.
6. **Prove the connection.** Follow [runtime.md](runtime.md): test genuinely fresh sessions inside the workspace and from an unrelated directory, inspect the observed bootstrap, and record real evidence. If you cannot launch a fresh session, give the owner the exact test prompt and keep the connection unverified until they complete it. Run `doctor` and report remaining pending checks instead of claiming success.
7. **Open and explain the vault.** Show the owner the exact `Knowledge Base` folder to open in Obsidian. It starts with generic notes for core navigation and policies; Projects, People, and Personal indexes; task lists and daily records; memory logs and summary areas; and agent hats, five software workflows, completion guidance, rules, roster, and capability indexes. No personal notes or histories are supplied. Ask what project or goal they want to add first.

After installation, the owner works through ordinary conversation. During authorized work, agents follow the continuity loop to update linked notes, record decisions, validate changes, and sync the private backup. The notes do not think or update themselves: ongoing knowledge maintenance happens during agent sessions. Optional scheduled backup runs Git checks without invoking AI.

## Connect another agent to the same vault

Give the new local agent this prompt, replacing the workspace path:

> Connect yourself to my existing ASK workspace at WORKSPACE_PATH using its installed tools in WORKSPACE_PATH/system/scripts/. Resolve the vault using bootstrap --workspace WORKSPACE_PATH (default Knowledge Base, with optional system/settings.ini overrides or existing legacy configuration), then read date.md, INDEX.md, agents.md, and knowledge-map.md under that vault in order. Follow WORKSPACE_PATH/system/docs/runtime.md to persist this bootstrap in your actual runtime, preserving existing instructions. Follow WORKSPACE_PATH/system/docs/onboarding.md to reconcile your local identity and agreed scope in my existing roster, and inventory all currently exposed skills when feasible and document scoped integrations and runtime/surface limits in the existing capability catalogs. Preserve other agents and custom notes; do not install anything or inspect credentials to build an inventory. Use the vault's continuity process for authorized edits. Verify fresh sessions inside and outside the workspace. Reuse the existing vault and backup; do not create another vault. Report any manual or unverified step.

From the ASK workspace, the connection command is:

```sh
python3 system/scripts/ask.py agent connect --workspace /path/to/your-workspace --runtime claude
```

Use `codex`, `cursor`, or the other runtime's name as appropriate. Follow with the status and verification commands in [runtime.md](runtime.md). Each runtime needs its own persistent registration and proof. This does not grant a remote or browser-only agent access to local files; the owner must provide a supported connection first.

## Share ASK with another person

Send them the public repository link and the README prompt. They repeat installation using their own folders, agent accounts, and private GitHub repository. They do not register with the project's author or receive access to anyone else's vault. Shared team vaults and their permissions need a separate, explicit setup.
