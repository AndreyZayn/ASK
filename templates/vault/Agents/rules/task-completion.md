# Task Completion Contract

Start with a compact checkpoint in the existing conversation or task record: outcome and acceptance criteria; repository, branch or environment and delivery target; actions already authorized; and owner. A clear fix or implementation request is enough to start. Later corrections refine that objective without erasing completed work.

For substantial work, establish applicable runtime, representative data, access, and delivery dependencies early. Configuration is not evidence of working connectivity. Identify missing dependencies and their next owner while continuing independent work.

Implement, verify, repair, and deliver within the actual target. Do not turn a planning request into implementation or a PR request into merge or production deployment. Preserve pauses, cancellations, budgets, and stricter runtime rules. After two unsuccessful repairs of the same problem, change strategy before trying again. Never change routes to bypass a permission denial.

A blocker applies only to dependent work after permitted recovery paths have been exhausted. Before an unfinished handoff, reconcile the latest instructions, completed artifacts, remaining criteria, attempted recovery, blocked dependency, next owner, and exact resume condition. A failed push does not prevent independent verification or documentation.

Close at the authorized target with observed evidence. Delegation does not transfer overall ownership: the controller reconciles worker outputs, task state, and [[knowledge-continuity-loop|continuity]]. No separate completion CLI, task board, or lifecycle hook is required by this contract.
